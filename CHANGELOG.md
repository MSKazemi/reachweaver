# Changelog

All notable changes to ReachWeaver are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/). `scripts/release_gate.py` requires a non-empty section for the version in `pyproject.toml`, and a `YYYY-MM-DD` date on it before a tag is created (`make release-gate TAG=vX.Y.Z`).

No section below claims a growth result. The only delivered posts claimed are the Bluesky and Mastodon text posts of 2026-10-11, recorded as first-party receipts in [docs/receipts/](docs/receipts/) (see the Unreleased section).

## [Unreleased]

### Fixed

- **`workspace --init` from the pip package now creates `config/accounts.json`.** The example accounts file now ships inside the package (`reachweaver/accounts.example.json`, kept byte-equal to `config/accounts.example.json` by a test), so a user who runs `pipx install reachweaver` and `reachweaver workspace --init .` no longer meets "Missing .../config/accounts.json" at the first `doctor`. The package smoke check (`scripts/check_package.py --smoke`) now runs that exact sequence in a clean environment. Affects 0.5.2 from PyPI; fixed in the next release. No change to approval, dry-run, emergency-stop or credential rules.

### Documentation

- **ReachWeaver is on PyPI.** 0.5.2 was the first upload, by the release workflow's `pypi` job after the owner approved the `pypi` deployment; the PyPI files have the same SHA-256 as the GitHub release assets, and `pipx install reachweaver` installs it. The README and [docs/PACKAGING.md](docs/PACKAGING.md) now say so.

## [0.5.2] - 2026-10-16

The first release that can publish ReachWeaver to PyPI. The release workflow has an optional third job, `pypi`, that uploads the wheel and source archive already attached to the GitHub Release by trusted publishing (no stored token), after the owner approves the `pypi` deployment. A patch version: no command, option or default of the tool changed.

**Upgrade notes.** None for the tool. Once the first upload has succeeded, `pip install reachweaver` and `pipx install reachweaver` work in addition to installing the wheel from the release page ([docs/PACKAGING.md](docs/PACKAGING.md)).

### Added

- **Optional PyPI publishing by trusted publishing, prepared and off (owner go-ahead, 2026-10-16).** The release workflow gains a third job, `pypi`, that runs only after `publish`, only for the repository owner, only when the repository variable `PYPI_PUBLISH` is `true`, and only after the owner approves the `pypi` GitHub environment (created, with the owner as required reviewer and restricted to `v*` tags). It checks out nothing and builds nothing: it downloads the wheel and sdist from the GitHub Release, verifies them against `python-dist.sha256` and uploads exactly those files with `pypa/gh-action-pypi-publish` (pinned to a full commit SHA, v1.14.2). Its only extra permission is `id-token: write`; there is no stored PyPI token. Nothing is published until the owner creates a pending publisher on PyPI and sets `PYPI_PUBLISH` (steps in [docs/PACKAGING.md](docs/PACKAGING.md)). `publish` keeps `contents: write` as its only write. `tests/test_release_workflow.py` (`ReleaseWorkflowPyPITests`) and `tests/test_packaging_metadata.py` now pin the three-job model. The job has not run against PyPI.

## [0.5.1] - 2026-10-16

ReachWeaver is now also a standard Python package, built and checked by CI and attached to every release: a wheel, a source archive and `python-dist.sha256`, next to `skill.zip`. A patch version: no command, option or default changed, and the clearer `doctor`/`health` output and dashboard wording from the previous merge ship with it.

**Upgrade notes.** None. The Claude Code plugin and `reachweaver update` are unchanged. To use the package instead: `pipx install` the wheel from the release page ([docs/PACKAGING.md](docs/PACKAGING.md)).

### Packaging and CI

- **Release assets:** the `publish` job of the release workflow rebuilds the wheel and sdist, checks them, writes `python-dist.sha256` (the wheel and the sdist) and attaches all three with the skill bundle. It keeps its one write permission (`contents: write`) and the owner-only guard; no job, permission or trigger was added.
- **CI `package` job (every push and pull request, read-only):** builds the sdist and wheel with `build` 1.6.1, runs `twine check --strict` (`twine` 7.0.0), runs `scripts/check_package.py` and uploads the result as the `reachweaver-python-dist` artifact. The release workflow's read-only `verify` job runs the same steps before anything is published.
- **`scripts/check_package.py [--smoke]` (new, stdlib only):** compares the wheel and sdist with the checkout (one wheel, one sdist, version in the archive names, `pyproject.toml` and the code, every runtime module and bundled registry present and nothing extra, entry point, license files, Apache-2.0 expression, no runtime dependency, Python >= 3.11) and refuses anything private in either archive (docs, `.claude`, state, databases, `.env*` files, local accounts, security-review notes, an approval ledger, a workspace marker). `--smoke` installs the wheel into a fresh virtual environment and runs `reachweaver version`, `capabilities` and `distribution-plan` from an empty folder. `make package` runs the same checks locally.
- **`pyproject.toml`:** complete metadata (SPDX `license = "Apache-2.0"` with `license-files`, classifiers, project URLs; `setuptools>=77`). A test now fails if a registry JSON is added to `reachweaver/` without a `package-data` entry. There is deliberately no `MANIFEST.in`, so a source archive built from a working folder holds only the package, the tests, the README and the licenses.
- **Not done, on purpose:** PyPI publication, GitHub build-provenance attestations and a container image. GitHub Packages has no Python registry; PyPI needs an account, a publisher and terms accepted by the owner; attestations and trusted publishing need extra workflow permissions that change the audited release model. [docs/PACKAGING.md](docs/PACKAGING.md) lists the exact steps and what must be reviewed first.
- `tests/test_check_package.py` (16) and `tests/test_packaging_metadata.py` (14) pin all of this, including that the README's wheel link always matches the current version.

### Changed

- **Clearer `doctor` and `health` at a terminal; dashboard wording.** At a terminal `doctor` leads with a one-line verdict and an aligned account table, and `health` with the readiness verdict, a per-account table, only what needs attention and one "Next:" line (a credentials-only block says that drafting, review and dry runs still work). Piped output and `--json` are byte-identical. The dashboard shows "not scheduled" instead of "unknown" for an unset schedule, an ok/missing credentials chip per account, and the same credentials-only explanation on the Overview banner. Fixed: a terminal that reports 0 columns (some ptys, `script`) squeezed every table to its minimum width.

## [0.5.0] - 2026-10-16

Everything that is yours in one folder, and a readable record of what you posted: a workspace folder you can copy to another computer (`workspace`, `media-relink`, a global `--home`), a posting journal and archive (`journal`, `archive`), and the read-only local dashboard with friendlier terminal output (`ui`, `start`, `completion`). 7 new commands (92 in all, none removed). A minor version because it adds commands and a global option.

**Upgrade notes (behaviour you may notice).**
1. **Nothing changes until you opt in to a workspace.** The new `.reachweaver-workspace` marker file is what makes a folder a workspace; without it every default path stays relative to the folder you run from, exactly as before. To adopt a folder that already has `config/` and `state/`, run `reachweaver workspace --init .` inside it: it only adds the marker and missing sub-folders and never overwrites or moves anything.
2. **An explicit `--db` / `--accounts`, or a `REACHWEAVER_DB` / `REACHWEAVER_ACCOUNTS` setting, still wins** over a workspace.
3. **After copying a workspace to another computer** run `reachweaver workspace --repair --apply` so attachments recorded by absolute path are found again in `media/`. Credentials are never stored in the folder and must be set again.
4. **Nothing is archived automatically at send time.** `archive --copy-files` is something you run; changing the send path needs its own security review.

### Added

- **One folder for everything that is yours (owner request, 2026-10-16).** `workspace --init [DIR]` creates a single workspace folder (`config/`, `state/` with the database, approval ledger and archive, `media/`, `logs/`, a `.reachweaver-workspace` marker, a README and a `secrets.env.example` of variable names only) and never overwrites or moves existing files, so an existing `config/` + `state/` folder is adopted in place. Commands run from inside the folder, from any sub-folder, or with the new global `--home DIR` use it automatically (`reachweaver/home.py` resolves the default paths for the database, accounts, opt-out list, caps and retention policy; an explicit flag or `REACHWEAVER_*` setting still wins, and a folder without the marker behaves exactly as before). `workspace --gather [--apply]` copies attachments of unsent posts into `media/` (hash-verified), and after copying the folder to another computer `workspace --repair [--apply]` re-finds them in `media/` by size and SHA-256 and fixes the recorded paths, so approved posts stay approved. The report also warns about a secrets file sitting in the folder. `tests/test_workspace_folder.py` (14) walks the whole story: copy the folder, delete the original, repair, and the post is still approved.
- **`workspace` and `media-relink`: moving your data to another computer (owner question, 2026-10-16).** Your data was already separate from the program: `config/` (account metadata, never a secret) and `state/` (the database, the approval ledger next to it, the archive), with credentials only in the environment. `workspace` (read-only, exit 1 when a copy would not work) now says so concretely: where each file is, database integrity, whether the approval ledger still matches the database, a `-journal`/`-wal` file meaning a run is in progress, credential variable NAMES missing on this computer, and which recorded attachment files are missing or changed (attachments are stored by absolute path and SHA-256, so unsent posts need them at the recorded path). `media-relink --from OLD --to NEW [--apply]` repairs that after a move: dry run by default, only posts that are not sent and not in flight, a path is written only after the file at the new location is read and matches the recorded SHA-256, and `storage.rewrite_attachment_paths` proves in one transaction that the approval hash is unchanged (it rolls back otherwise), so relinked posts stay approved. New `accounts.accounts_path()` exposes the existing default resolution. See [docs/MOVING.md](docs/MOVING.md). `tests/test_workspace.py` (19), including a real copy of a workspace to another folder.
- **`journal` and `archive`: a readable record of what was posted (owner request, 2026-10-16).** `journal` is read-only and lists every post that went out or may have (`published`, `sending`, `needs_review`; `--all-statuses` adds the rest) together with material recorded by `mark-shared`: the exact text, UTC time, platform and account, status, approver and approval time, the first 12 characters of the approval hash, the link the platform returned, an audit timeline of fixed action codes (the free-text event detail, which can hold provider text, is never shown), and each image and video with path, SHA-256, size, type and whether the file is still on disk (`--verify-files` also re-hashes it). Filters: `--post-id`, `--platform`, `--account`, `--since`, `--until`, `--limit`; formats: table, markdown, csv (spreadsheet formulas neutralised) and json; `--out FILE` writes a new owner-only file. `archive` writes a private folder (0700/0600, `state/archive/` next to the database by default): one sub-folder per post with `post.txt` (the exact text), `meta.json` and, with `--copy-files`, copies that are made only if the file still matches the SHA-256 recorded when it was attached, plus `index.md` and `index.csv`. It only ever adds, never overwrites a post folder, and refuses a folder that is not an archive. Neither command sends, schedules, approves or contacts anything, and nothing is archived automatically at send time (that would change the send path and needs its own security review). See [docs/JOURNAL.md](docs/JOURNAL.md). `tests/test_journal.py` (18).

## [0.4.0] - 2026-10-16

Made for use inside Claude Code on a subscription, and safer against posting the same thing twice: a guided way to connect accounts, a repeat guard, seven more channels (100 in all), a rewritten README and docs for newcomers, and a skill that loads about a third of the text it used to. 3 new commands (85 in all, none removed). A minor version because `approve` gains a new refusal (below).

**Upgrade notes (behaviour you may notice).**
1. **`approve` refuses an exact repeat.** If the same account has already published, sent, left unresolved, or recorded with `mark-shared` the same video file, image file or identical wording on the platform, `approve` refuses and `check` prints `BLOCKED`. Re-approving an identical evergreen post now needs `approve POST_ID --allow-repeat`, which leaves a `repeat_override` audit event. Similar wording, another account and the same link only warn.
2. **A new `shared_material` table** is created, empty, the first time a database is opened. Nothing existing is migrated or changed.
3. **The skill is smaller.** `SKILL.md` went from about 37.5 KB to about 12.7 KB; the removed detail moved unchanged into `references/routing-detail.md`, `references/workflows.md` and `references/cli-cookbook.md`, which Claude loads only when a request needs them. No behaviour changed.

### Added

- **Skill optimised for Claude Code on a subscription.** `SKILL.md` now opens with a statement that ReachWeaver makes no model calls and needs no API key, keeps the router and the rules that override reach targets, and loads detail on demand from three new references (`routing-detail.md`, `workflows.md`, `cli-cookbook.md`; the text was moved verbatim). New [docs/CLAUDE-CODE.md](docs/CLAUDE-CODE.md) covers install, a first session, who does what and how to keep usage low. `tests/test_skill_budget.py` fails if `SKILL.md` grows past 16 KB or any source file calls a paid model API.
- **Repeat guard: do not post the same material twice (owner request, 2026-10-16).** `repeat-check` (read-only) and `mark-shared` are new; `check`, `show` and `approve` now compare a draft with the platform's history. Compared: the exact bytes of the video file and of each image (SHA-256), the wording (word 3-gram overlap, the measure `campaign-check --history-db` already uses; identical is an exact repeat, 60% or more is similar) and the canonical link. History is every non-cancelled post for the platform in the local database plus the new `shared_material` ledger of things posted by hand. An exact video, image or wording repeat of material **this account** has already shared (published, `sending`, `needs_review`, or recorded by hand) makes `check` print `BLOCKED` and `approve` refuse, unless the owner passes `approve --allow-repeat`, which records a `repeat_override` audit event. Everything else (similar wording, queued twins, another account on the same platform, the same link) is a warning. The same file on another platform is never a repeat. Reports carry ids, statuses and dates, never the earlier post's text. Limits: exact files and wording only (a re-encoded video is not recognised), nothing is read from the platform, and the check runs at `check`/`show`/`approve`, not again at send time. See [docs/REPEAT-GUARD.md](docs/REPEAT-GUARD.md). The approval step gains one more precondition and a human-only override; the send claim, dry-run default, pause, credential isolation and reconciliation are unchanged, and a send-time recheck is deliberately left for a separate security review.
- **Fixed in `connect` (found while testing this):** with an existing database the status table raised `UnboundLocalError`, because a local import in the same function shadowed the read-only opener. `tests/test_repeat_guard.py` now covers it.
- **Seven more channels in the distribution registry (93 to 100), all manual-only (2026-10-16).** PeerTube (scheduled publication is documented for PeerTube 6.0 or later when the instance enables it), Nostr, Farcaster, Pixelfed, HackerNoon, and the human-only Matrix rooms and Kaggle. Each entry cites the official page that was fetched; where a page is rendered by script and nothing about scheduling or rules could be read, the entry says `unverified` instead of guessing. Patreon, Ko-fi and Dailymotion were left out because their official pages returned a 403 challenge to a direct fetch. No adapter, account connection or ranking was added; `distribution-plan` rankings are unchanged.
- **`connect`: a guided way to connect your accounts (experimental, owner-chosen 2026-10-16).** `reachweaver connect` prints an offline status table (credential variable names only; nothing is read from the network or written to the database). `reachweaver connect --guide` walks through the accounts one at a time with you at a terminal: the official sign-in page and steps per platform (Bluesky, Mastodon, Telegram, LinkedIn), a hidden-input way to set each variable, and then, only after you answer `y` for that account, the same read-only identity check as `connect-check --online`. It asks for no secret, opens no browser, posts nothing, leaves approval, dry-run, pause, credential and reconciliation rules untouched, and refuses to run without an interactive terminal. `tests/test_connect_guide.py` (20) pins this, including a static check that the module cannot read the environment, open a browser or touch the network.

### Documentation

- **README rewritten as a front page for newcomers.** It now opens with what ReachWeaver is in plain words, what it will never do, which platforms really work today, how one post travels from draft to approval, three ways to get started and the five commands most people use. The honest-limits statement, the liability notice and the read/run/send disclosure are unchanged. The full command list stays in the README (collapsed), because the release gate requires every subcommand to be named there.
- **New [Start here](docs/START-HERE.md) guide, [glossary](docs/GLOSSARY.md) and [documentation index by goal](docs/README.md).** The long feature guides that used to fill the README moved unchanged to [docs/FEATURES.md](docs/FEATURES.md) (links adjusted).
- The quickstart and troubleshooting pages point newcomers to the guide and glossary; the quickstart no longer calls `approval-mode --max-age-hours` a draft.
- `tests/test_plain_language_docs.py` pins the structure; `tests/test_readme_channel_count.py` also checks the channel count in FEATURES.md.

## [0.3.0] - 2026-10-16

The first release since 0.2.0: 149 commits, 13 new commands (82 in all, none removed), and the first live receipts. A minor version, not a patch, because it adds commands and changes two defaults (below). The section lists are the full record; the highlights:

- **First live receipts.** One approved text post each was sent through ReachWeaver to Bluesky and Mastodon on 2026-10-11 and re-observed from the platforms' public APIs on 2026-10-15 ([docs/receipts/](docs/receipts/)). Telegram and LinkedIn have none; every other adapter stays disabled until its own supervised receipt.
- **New commands.** `calendar-gaps`, `link-health`, `delivery-options`, `manual-export-batch`, `engagement-queue`, `seo-content-check`, `profile-audit` and `post-audit` (profile CSV, cross-platform consistency), `suggest`, `weekly-digest`, `peer-benchmark`, `disconnect` and `reconnect`.
- **Safety, owner-reviewed.** Account hold after an unresolved send, approval expiry (opt-in), account disconnect with a terminal-only reconnect, rights on attached images bound under `approval/media-2`, a documented API cost note in `show` and the dry run, branch protection and a hermetic test for the ignore rules.
- **Research and docs.** 92 distribution channels with dated sources and a platform-matrix table, a regional API feasibility matrix, the Mastodon guide, owner-run pilot runbooks, and the browser-assist decision (not planned).

**Upgrade notes (behaviour you may notice).**
1. **Account hold is on by default.** While any post of an account is `needs_review`, or `sending` for over 15 minutes, no other post is claimed for that account (`account_unresolved_send_hold`) until you check the native account and run `reconcile` or `cancel` on that post. There is no bypass flag.
2. **Images that carry a rights record are approved under `approval/media-2`.** Images without one, and every existing approval, keep `approval/media-1` unchanged. Approval expiry (`approval-mode --max-age-hours`) is off until you set it.

### Security

- **Rights on attached images: license, attribution, provenance and alt translations (issue #48, owner-reviewed and merged 2026-10-15, PR #73).** An image attached with `media-attach` can now carry an optional rights record (`--rights-confirmed --license ID --created-by owner|tool|third_party`, `--attribution`, `--tool`, `--rights-source-url`, repeatable `--alt-translation LANG=TEXT`), validated with the same rules as the `media-check` manifest (SPDX or `owner`/`licensed`, third-party media needs a real license and attribution, `CC-BY*` needs attribution, tool-made media names the tool and prints a disclosure note, translations validated like alt text). It is stored in `media_json`, shown by `show` and the confirmation display, and **bound by the approval hash under the new tag `approval/media-2`**: changing the license, attribution, provenance or a translation after approval invalidates it. An image without a rights record keeps `approval/media-1` byte for byte, so every existing approval still verifies. Rights text is never published and nothing is fetched. Tests: `tests/test_media_rights.py` (18) and the tag pins in `tests/test_binding_tags.py`. Changes what the approval binds for new images; owner-reviewed as a security change and merged 2026-10-15 (PR #73).
- **`disconnect` and `reconnect` (issue #38, owner-reviewed and merged 2026-10-15, PR #72).** `disconnect --account ID` is a tighten-only local action: it stores one `account_disconnected:<id>` settings row (any stored value counts) and an audit event; the send claim then refuses the account (`account_disconnected`, post stays approved, nothing written or budgeted), `publish --live` skips it before any credential check or request, the dry run reports it, and `connect-check` shows `local_state`. It prints the credential variable **names** the account reads (never values) and generic revocation steps, and revokes nothing itself. `reconnect --account ID` is human-only: it needs an interactive terminal on stdin and stdout and a fresh 32-byte challenge typed on `/dev/tty` (the ritual that turns off human confirmation); a failed ritual changes nothing. Worker logs gain the skip reason `account_disconnected`. Tests: `tests/test_account_disconnect.py` (16; seven fail without the enforcement). Touches the send claim; owner-reviewed as a security change and merged 2026-10-15 (PR #72).
- **Account hold after an unresolved send (issue #41, owner-reviewed and merged 2026-10-15, PR #71).** While any post of an account is `needs_review`, or `sending` for over 15 minutes, no other post is claimed for that account: `publish --live` prints `SKIPPED ...: account_unresolved_send_hold`, before the identity preflight and again inside the claim lock; the post stays approved/scheduled, no budget is used, nothing is written, and the dry run reports it. The hold is derived from the posts table (no new table or setting), applies per account, and is lifted only by `reconcile` on the post that causes it; there is no bypass flag. A live `sending` post newer than the reconcile threshold does not hold. Worker logs gain the skip reason `unresolved_send_hold`. Tests: `tests/test_account_hold.py` (12; eight fail without the hold); existing fixtures that seeded several unresolved sends on one account now use the test-only `tests/hold_support.py`. Touches the send claim; owner-reviewed as a security change and merged 2026-10-15 (PR #71).
- **Tag releases split into a read-only `verify` job and an owner-only `publish` job (private #50, #51).** `.github/workflows/release.yml` now defaults to `contents: read`; `verify` (checkout with `fetch-depth: 0` and `persist-credentials: false`) runs the new `scripts/release_ref_guard.py`, the secret scan, stdlib lint, compileall, runtime-dependency guard, Ruff and mypy with the same pins and flags as `ci.yml`, `sync_skill.py --check`, the tag/version check and `release_gate.py --tag` with tests; `publish` needs `verify`, runs only when the pushing and triggering actors are the repository owner, is the only job with `contents: write`, tests `skill.zip` and its checksum, re-runs the guard and calls `gh release create --verify-tag`. The stdlib guard reads `GITHUB_*` variables and local `git rev-parse` only (no token, no network) and fails closed unless the run is a tag push of exactly `vMAJOR.MINOR.PATCH` by the owner (login and account id) and the checkout, tag, `GITHUB_SHA` and `origin/main` are one commit. Tests: `tests/test_release_ref_guard.py` (16, against real temporary local git repositories) and `tests/test_release_workflow.py` (16, was 7). Docs: "Maintainer release checks" in `docs/RELEASE-PLAYBOOK.md`, `docs/SECURITY-CHECKLIST.md`. Branch protection is a GitHub setting this cannot turn on, and a green run is not legal clearance or a social-platform receipt. No tag or release was made.
- **Opt-in approval expiry (issue #39, owner-reviewed and merged 2026-10-15, PR #70).** `approval-mode --max-age-hours N` sets a time-to-live on approvals, **off by default**. When set, a post approved more than N hours ago is `approval_expired_reapproval_required` in the send claim, `schedule`, `calendar-plan --apply`, `health` and `show` (which prints `approval_expires_at`): it stays approved or scheduled, nothing is sent, no budget is used, and one audit event is written; re-approving starts a new window. The check runs last so tampering keeps its own reason code; `schedule` refuses a due time after the approval would lapse; the setting is tighten-only (only a lower value is accepted by a command) and an unreadable stored value fails closed. ### Fixed

- **`ops-metrics --out` could overwrite the state database (issue #26, review F1).** `--out` atomically replaced any path, so `--out state/reachweaver.sqlite` replaced the database with metrics text, set it to mode 0644 and printed `database unchanged`. `ops_metrics.write_textfile` now refuses, with exit 2 and nothing written, the database itself (same path, same resolved path or a hard link, via `os.path.samefile`), any symbolic link, a directory, and an existing file whose name does not end in `.prom` or `.json`; a new file may have any name. - **`ops-metrics --since 999999d` crashed with an `OverflowError` traceback (issue #26, review F1).** The relative amount is now bounded by the 3650-day limit before any date arithmetic, `--now` must lie between 1970 and 9998, and `storage.parse_utc` turns an out-of-range date such as `0001-01-01T00:00:00+01:00` into a ValidationError (exit 2) for every command that parses a date.
- **`engagement-fetch` cut reply text before redacting it (issue #17, review F1).** An e-mail address, token or phone number crossing the 4000-character cap was seen only partially by the redaction patterns, so a fragment such as `john.doe@examp` or the first 4000 characters of a JWT reached the export. - **A credential with a control character could leak into `ERROR:` output (issue #5, review F1).** A `$CREDENTIALS_DIRECTORY` file ending in `\r\n` kept its `\r`, `http.client` refused the header with `ValueError("Invalid header value b'Bearer <token>\\r'")`, and the CLI printed that message, token included. `accounts.credential` now strips exactly one trailing `\n` or `\r\n` from a file and refuses any value, from a file or the environment, that still contains a C0 control character or DEL (`credential NAME contains control characters`, name only). Tests: `ControlCharacterCredentialTests`, `ControlCharacterCliTests`, `RequestBuildErrorTests` in `tests/test_hardening.py`.

### Fixed

- `media-check` subtitle URL warnings show only scheme, host and path (`?…` marks a hidden query or fragment); a translated cue's `?token=` query string or `user:password@` no longer reaches the report.
- **Release gate: human-only rows can no longer drop their `distribution_id`.** The human-only ⇒ `blocked` rule ran only when a scorecard row had `distribution_id`, so deleting it from the `hacker_news` row let that row claim `offline_mock_tested`. A row whose `id` or `capability_id` names a human-only distribution-registry entry must now carry that entry as `distribution_id` and be `blocked` (`scripts/release_gate.py`; `ReleaseReadinessScorecard` in `tests/test_onboarding.py`).
- **`media-check` translated subtitles.** A URL that a translated cue adds and its source cue lacks is now a warning (a link injected during translation is a phishing risk). Digit runs are normalised as text instead of `str(int(run))`, which raised `ValueError` past Python's 4300-digit limit; leading zeros are ignored and long runs are shortened in findings. An SRT index such as `²` or `①` (accepted by `str.isdigit()`, rejected by `int()`) crashed the check and is now a "numeric index" error, and an over-long timestamp hour field is a malformed timestamp instead of an `int()`/`float()` overflow. Locale tags compare case-insensitively (RFC 5646), so an `en-us` track is the source of an `en-US` asset and `target_locales` matching ignores case. See [docs/MEDIA-ASSETS.md](docs/MEDIA-ASSETS.md#translated-subtitle-tracks).
- **`calendar-plan --audience-activity` DST fall-back collision.** When a fall-back in the planner zone mapped two activity hours to the same local slot (UTC CSV, `as_of` 2026-10-21, Europe/Rome: Sunday 00:00 and 01:00 UTC are both 02:00), the lower-ranked hour's provenance overwrote the top hour's and one top hour was lost. `audience.derive_slots` now keeps the higher-ranked hour, warns with the dropped hour, and fills from the next-ranked hour; `calendar.propose_calendar` also keeps the first provenance per window. See [docs/CALENDAR-PLANNER.md](docs/CALENDAR-PLANNER.md).
- **Similarity tokenizer and zero-width spaces in Thai, Lao, Khmer and Myanmar.** Dropping every format character also removed U+200B where these scripts use it as the word break, so a one-word edit in ZWSP-segmented Thai scored 0.00 instead of 0.40. U+200B next to a letter of those scripts is now a space; elsewhere it, the joiners, word joiner, BOM, soft hyphen and bidi controls are still dropped, so the zero-width evasion tests stay green. See [docs/CLAIM-GROUNDING.md](docs/CLAIM-GROUNDING.md#posting-history).
- **Markdown table escaping.** `media-storyboard` put the owner's `--safe-zones` source URL (and campaign ids) into its Markdown tables raw, so a `|`, backtick or newline could add cells or rows; these cells are now escaped. `report --format markdown` cells now also escape backslash, backtick, `[ ] ( ) * _` (CommonMark backslash escapes) besides pipes and HTML, as defence in depth (`report_format.markdown_cell`).
- `media-check` now rejects SRT or WebVTT subtitle files that still contain an unresolved placeholder or TODO.
- `reachweaver.__version__` said `0.1.0` while `pyproject.toml` said `0.2.0`. Both now say `0.2.0`, and the release gate fails on any mismatch.
- The README five-minute setup scheduled a post for a future time and then ran `publish --post-id`, which refuses posts that are not yet due. The preview now runs before `schedule`.
