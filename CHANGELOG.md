# Changelog

All notable changes to ReachWeaver are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/). `scripts/release_gate.py` requires a non-empty section for the version in `pyproject.toml`, and a `YYYY-MM-DD` date on it before a tag is created (`make release-gate TAG=vX.Y.Z`).

No section below claims a growth result. The only delivered posts claimed are the Bluesky and Mastodon text posts of 2026-10-11, recorded as first-party receipts in [docs/receipts/](docs/receipts/) (see the Unreleased section).

## [Unreleased]

### Security

- `published_manual` is born terminal: `transition` has no edge into or out of it (approve, unapprove, cancel and schedule refuse it), `reconcile` refuses it, and `pending`, `claim_sending`, `publish` (dry run and `--live`, with or without `--post-id` or `--scheduled-only`), the Postiz and TikTok runners, the media/video setters, `queue-health`, `dead-letter` and the approval-ledger audit never select it. Every approval column of the record is NULL. Covered by `tests/test_manual_published.py`. No send path, network endpoint or credential use was added.
- **AI-content label precondition for posts with media** (owner-approved 2026-10-21, security review decisions D1-D4 and D6; D5 deferred). `approve` of a post with images or a video computes the `ai-label-check` decision for the post's own platform from its stored declarations (EU Art. 50 left out, D4) and refuses with `ai_label_unanswered` when it is `required` or `unknown` (D2), until you pass `approve --ai-label applied|not_needed`. Text-only posts are never blocked (D1); `check` and `show` print the advice and, where relevant, the EU Art. 50 hint (advisory, never blocks). For a post with media, the declarations and the answer are bound into the approval hash under the add-on tag `reachweaver.storage.approval/media-3` (D3), so changing one after approval refuses the send; the `approve` audit event records `ai_label_decision=... ai_label=...`. `claim_sending`, `check_approval_binding`, `schedule`, `publish` (dry run) and `health` re-run the same decision on the bound values and the bundled registry, with no network, and refuse `ai_label_unanswered` when a needed answer is not bound. The registry file is not bound. `health` warns (`ai_disclosure_registry_aging`, attention, never blocks) when the AI-disclosure rules are more than 90 days old (D6). Nothing is added to the send path: no platform label field is set.
- Browser composer write path (`share --web`, owner-approved 2026-10-21): every new route (`/api/packages`, `/api/package/open`, `/api/package/duplicate`, `/api/mark-posted`, `/api/draft/load|save|clear`, `/api/media`) needs the loopback Host, the per-run token and the exact Origin; JSON bodies stay at 96 KiB, a photo/video at 256 MiB with the `share --attach` extension allowlist. Package names must match `share-YYYYMMDD-HHMMSS-<12 hex>`, media ids 16 hex digits, and every path is resolved and confirmed to sit directly inside its private 0700 folder; symlinks are refused and never followed (`O_NOFOLLOW`, `O_EXCL`). An update needs `confirm: true` and the revision the editor loaded (409 otherwise) and is refused once any network is marked posted. The only database write is `storage.record_manual_publish` (terminal `published_manual`); nothing can approve, schedule or send. The read-only dashboard (`ui`) is unchanged and still refuses every write method. Covered by `tests/test_share_browser_composer.py`.

### Added

- **`platform-risk` (new, read-only): how much of your reach depends on one platform.** Per account, per persona and overall, the share of your recorded reach per platform: `--metric views|impressions` at a matched post age (`--age-hours`, default 168; nearest exact snapshot, windowed ones skipped, never summed), else the latest exact value labelled `latest_not_age_matched`. When a platform in a scope has no measured post, the scope falls back to post counts (published posts plus recorded manual shares) and says `FALLBACK`. Concentration: top-platform share, HHI (0-1 and points) and effective platforms, with `concentrated`/`few`/`spread` labels that are editorial thresholds. Owned channels (`site`, `blog`, `newsletter`, `email`, `--owned ID`, owner-stated `--owned-reach NAME=N`/`--owned-posts NAME=N`) give an owned share. Advice lines are hypotheses with a way to check them; `--site`/`--setup` reuse `social-web-plan`'s canonical home. `--json` (kind `reachweaver.platform-risk` v1). Database opened `mode=ro`, never created; no network, queue or send path. Guide: [docs/PLATFORM-RISK.md](docs/PLATFORM-RISK.md).
- **`reachweaver/platform_risk_registry.json` (new, shipped in the wheel and the skill bundle).** Sourced risk flags, each with an official URL, the exact quote and checked date 2026-10-21: X pay-per-use API pricing, LinkedIn API Terms 3.1 on automated posting, Reddit's separate agreement for commercial Data API use, and the TikTok USDS Joint Venture (2026-01-23) retraining the US recommendation algorithm on US user data. Owned channels and concentration bands are labelled editorial. Validated by `platform_risk.validate_registry` and `tests/test_platform_risk.py`.
- **`--market US|global|PLATFORM@MARKET` on `calendar-plan`, `distribution-plan` and `platform-risk`.** When TikTok is in the plan, a `market_notices` entry flags that TikTok's US recommendation algorithm sits with a separate US joint venture since 2026-01-23, cites the announcement and asks you to re-verify with your own US audience data (`applies` true, false or null when no market is given). It only flags and cites: slots, rankings and `--apply` are unchanged, and no US/global difference is claimed.
- **`eu-review-evidence` (new, read-only): human-review evidence for the EU AI Act Art. 50(4) exemption.** For published posts (`--since`, `--account`, `--platform`, `--post-id`, `--limit`): who approved and how the name was obtained, when, the approved payload hash, a SHA-256 of the stored text, the opt-in human-confirmation token, the approval-ledger line for the post's nonce (consumed time, hash match) with `ledger.audit`'s integrity status, and the authorship declaration when the database has an authorship column (absent columns are handled). Each post is `recorded`, `partial` or `missing` with its gaps. Every format (`text`, `--json`, `--format markdown`) leads with "Evidence of human review recorded by ReachWeaver; not legal advice; wording from a secondary source (artificialintelligenceact.eu); verify on EUR-Lex." The database is opened `mode=ro` and the ledger read through its own read-only chain check: nothing is created, repaired, migrated or sent. Docs: [AI-CONTENT-LABELS.md](docs/AI-CONTENT-LABELS.md#human-review-evidence-report-eu-review-evidence). Tests: `tests/test_review_evidence.py`.
- **`share` for Bluesky, Mastodon, Telegram and LinkedIn (owner decision 2026-10-21).** These four text networks, which ReachWeaver can also send to through its API, are now offered as copy-only packages in `share`, `share --guide` and `share --web` (the browser marks them "Copy and post yourself · or connect it to send from ReachWeaver"). Each package is checked with the rule `draft` and `check` use (`policy.validate_post`), shows that rule as its text limit, adds an offline Bluesky link/tag preview, and says: "Copy and post it yourself; to send it from ReachWeaver instead, connect the account and use draft → review." Share still writes no database, send queue or post row (tested by hashing an existing database before and after) and records nothing; `mark-shared` stays the way to record a by-hand post. `bsky` is accepted as an alias.
- **Per-network caption fitting in `share`** (`reachweaver/share_tailor.py`, deterministic, no AI). When one network's copy is over its limit, it is shortened at the last word that fits, ends with "…" and is marked SHORTENED in the plan, OPEN-FIRST.md and that network's CHECKLIST.md, naming any hashtags that were cut. Limits are the ones ReachWeaver already applies: the `draft`/`check` rule for the four API networks, the sourced Threads, Instagram, TikTok and YouTube-description limits in `manual_export.FACTS`, and the conservative Facebook Pages cap. Networks with no known limit keep the text as written, with a note when it exceeds ReachWeaver's internal guardrail. Hashtags are never moved (no sourced rule exists). New flag `share --no-shorten` keeps an over-long copy, which then blocks as before.
- **Offline media checks in `share --attach`.** Without a media manifest, each attached photo or video is probed from its header (`media.check_file_for_targets`, new) and checked with the same sourced rows as `media-check` (container, size, duration, aspect ratio, dimensions, codecs, frame rate) for each network that has a table (Bluesky, Mastodon, Instagram, TikTok, LinkedIn, YouTube Shorts, DEV). Findings appear as `MEDIA PROBLEM` / `Media advice` lines and in `manual-export.json` (`share.media_checks`) and never block; values the source does not state or an unreadable header are listed as not checked. No ffprobe or other tool is used. Alt text, captions and rights still need a manifest.
- **`account-add PLATFORM`** (new command, offline): appends one correctly shaped public entry for bluesky, mastodon, telegram, linkedin, instagram, threads, tiktok, youtube or facebook to `config/accounts.json` (or `--accounts`, inside the workspace when one is active). It never asks for, accepts or writes a secret (secret-named fields are refused), prints the credential variable names to set yourself and points to `connect --guide`. With `--persona` the wrong-account guard applies (unknown persona, a username the profile records under another persona, or a profile conflict is refused). `start` mentions it for placeholder and missing accounts files. Tests: `tests/test_account_add.py`, `tests/test_share_everywhere.py`.

The same link recorded twice for a platform is refused. Without `--url`, `mark-shared` is unchanged. `storage.record_manual_publish(...)` is the one entry point, for the browser composer's planned "Mark as posted" button. Guide: [docs/MANUAL-EXPORT.md#measure-posts-you-shared-by-hand](docs/MANUAL-EXPORT.md#measure-posts-you-shared-by-hand). Tests: `tests/test_manual_published.py` (synthetic data, no network).

### Changed

- `share` no longer refuses Bluesky, Mastodon, Telegram and LinkedIn with "uses the separate draft, check, approve, publish flow": they get copy-only packages (above). Sending from ReachWeaver is still only the separate draft, review and approval flow; human-only (Hacker News and others) and moderator-only (Reddit) venues still get notes only. `manual-export` is unchanged and still covers `manual_only` destinations only.
- `share --attach` files are no longer described as "not validated": OPEN-FIRST.md and the plan report the offline header checks.
- `journal`: a record made with `mark-shared --url` is listed once (source `posted_by_hand`, status `published_manual`), not twice; `--no-by-hand` leaves it out too. The repeat guard compares only its `mark-shared` entry (same account scope as before), never the record itself, and a record is never reported as a repeat of its own entry.
- `data-purge`: the `published_content_days` redaction also covers `published_manual` text.
- `schema-export` lists `published_manual` posts as unmapped (no canonical state; no `PublishJob` or approval is invented).
- `report` opens the database read-only (`mode=ro`). A missing database prints the same empty report plus a note on stderr and is never created. An older schema is refused with a hint to run `init` and is never migrated. The output is otherwise identical.
- `share --web` now writes `composer.json` (the editor fields) and, when media are attached, a `media/` folder into each package it saves; `share --web` passes the global `--db` to Mark as posted.

### Upgrade note

- Schema: `shared_material` gains the nullable column `post_id` (added automatically by the usual migration). The `posts.status` CHECK of a database created before this version does not allow `published_manual`; the first `mark-shared --url` rebuilds the `posts` table once (SQLite's documented table-rebuild procedure in one transaction: every row and column is copied, approval hashes and MACs stay valid, `foreign_key_check` must pass, otherwise everything rolls back) and logs a `posts_status_check_widened` event. Nothing changes until then. Older ReachWeaver versions were not tested against a database that holds `published_manual` records; back up `state/` before downgrading.

### Upgrade notes

- The database gains three nullable `posts` columns (`authorship`, `realistic_synthetic_json`, `approved_ai_label`), added by `migrate()` on first open; older code ignores them. With all three NULL the approval payload is byte-identical, so **every existing approval keeps its hash**.
- **A post with images or a video approved before the upgrade is not grandfathered** (same rule as the approval nonce and send options): if its platform decision is `required` or `unknown`, the send is refused with `ai_label_unanswered` and the post stays approved or scheduled; `health` lists it under re-approval. Re-approve it once: `reachweaver unapprove POST_ID`, `reachweaver show POST_ID`, then approve with `--ai-label applied|not_needed` (or record `ai-declare` answers that settle it). Text-only approvals are unaffected. Every live adapter enabled today is text-only, so no enabled live send changes.
- Rollback: after a downgrade, an approval that bound declarations or an answer (`approval/media-3`) no longer matches the payload older code computes, so it is refused with `approval_hash_mismatch_reapproval_required` until re-approved (fails closed), as with earlier binding changes.

## [0.14.0] - 2026-10-21

Handier, smarter and aware of newer distribution paradigms. A short everyday `--help`, a first run that starts in the browser composer, `report --since`, and a `suggest` that works with no flags. `insights` learns what works from your own results. Every platform fact shows how old it is. `ai-visibility` checks what your own pages tell AI answer engines, `ai-label-check` gives per-platform AI-content label rules, and `social-web-plan` maps your reach across the fediverse, Bluesky and bridges. 125 commands (6 more than 0.13.0, none removed). Everything new is read-only or advisory; no live adapter is added.

### Added

- **`report --since WHEN`.** `24h`, `7d`, `30d` (hours or days, up to 3650 days), a date such as `2026-10-01` (midnight UTC) or an ISO 8601 time with a timezone. The report then covers only posts whose send started in the window and, for each, the latest snapshot observed in it (a post with only older snapshots counts as unknown, never 0); replies are filtered the same way. JSON gains a `window` object (`since`, `until`, `basis`) only when `--since` is given, Markdown a "Window:" line; CSV columns are unchanged. An unreadable value is refused with the accepted forms before the database is opened. `--since` adds no write. Tests: `tests/test_report_since.py`.
- **`reachweaver help [all|COMMAND]`**: the same text as `--help`, `--help all` and `COMMAND --help`. Read-only and offline; tagged `read_only` in the catalog.
- **`describe --json` marks the everyday commands** with a boolean `everyday` on every command entry (additive; `schema_version` stays 1). Every command is still listed.
- **Registry freshness: no command silently relies on a stale platform fact.** New `reachweaver/freshness.py` applies one age policy to every dated fact in the five bundled research registries (capabilities, distribution, discovery, profile-audit, sign-up): `fresh` up to 60 days, `aging` after 60, `stale` after 120 (the capability registry's existing threshold), `undated` when no checked date is recorded; a date is never inferred. New read-only command `reachweaver registry-age [--registry NAME] [--platform P] [--all] [--as-of YYYY-MM-DD] [--json]` lists the aging, stale and undated facts with their source, the counts per registry and the oldest checked date per platform; it reads only the bundled files, never creates the database and always exits 0. `health` prints a one-line summary, adds `global.registry_freshness`, a per-account `research_freshness` and the `attention` reasons `research_facts_stale` (a configured account's platform has a stale fact outside the capability registry, which keeps `registry_entry_stale`) and `research_registry_invalid`; neither changes the exit code. `doctor` prints the same line and carries `registry_freshness` in `--json`. `freshness.warning_line()` gives `context`/`start` a one-line warning to call later. Docs: [PLATFORMS.md#registry-freshness](docs/PLATFORMS.md#registry-freshness).
- **`insights`: "What works for you"** (read-only, offline). Compares your own published posts, per account, by time of day, weekday, weekday/weekend, text length, link, format (text/image/video), hashtag count, opening hook (question/number/statement) and each hashtag, using the result recorded about 7 days after posting (default `interactions` = likes + replies + reposts, the same matched-age snapshot rule as `baseline-eval`). Each group reports its median and count against the rest; fewer than 5 posts on either side is `too little data`, anything else is an `observation`, never a cause. Up to three "try more of / try less of" lines per account are phrased as hypotheses to test with `experiment-preregister`/`experiment-readout`; groups made of mostly the same posts are folded into one line. Filters `--account`, `--platform`, `--since 30d|DATE`; `--json` has a stable schema (`reachweaver.insights` version 1, see [docs/INSIGHTS.md](docs/INSIGHTS.md)). With too little data, or no database yet, it exits 0 and explains how to record results (`metrics-fetch`, `import-metrics`, `metrics`). It opens the database read-only, never creates or migrates it and has no network or send path. The dashboard's Results page shows the same lines under "What works for you". Tests: `tests/test_insights.py` (synthetic data only).
- **`ai-visibility`: what your own pages ask AI answer engines and search crawlers to do.** New read-only command. For each page it reports whether robots.txt allows or blocks `OAI-SearchBot`, `GPTBot`, `ChatGPT-User`, `PerplexityBot`, `Perplexity-User`, `Googlebot`, `Google-Extended` and `Bingbot`, and whether the file names the crawler or only reaches it through `*`. The matcher follows RFC 9309. Each crawler is shown with its role (search, training, or user-initiated fetch) and the operator's own words on what a block means. A blocked search crawler is a warning; a blocked training crawler or user-fetch agent is information. The report also checks `noindex`, `nosnippet` and `max-snippet` (meta tags and, online, `X-Robots-Tag`), Bing `noarchive`/`nocache`, title and description, `rel=canonical`, JSON-LD (whether it parses, and its `@type` values) and `<meta name="fediverse:creator">`. `/llms.txt` is reported as information only and labelled "optional; no major engine has confirmed it reads it"; Google says Search does not use such files. Offline (the default), it reads a saved page and robots.txt (`--url URL --html F --robots F`, or `--briefs F --page-id ID`). `--online` fetches only the `canonical_url` pages of your SEO briefs, their robots.txt and `/llms.txt`, through the `landing-check` guard (robots.txt honoured, redirects inspected, size caps, IPv4 first). No database, and nothing is drafted or sent. The report lists the operators' measurement tools (Search Console Generative AI performance report, Search Console platform properties, Bing Webmaster Tools AI Performance), and it quotes Google: meeting every requirement does not mean a page will be crawled, indexed or served. Guide: [docs/AI-SEARCH-VISIBILITY.md](docs/AI-SEARCH-VISIBILITY.md).
- **Sourced AI-search registry** `reachweaver/ai_search_registry.json` (packaged and mirrored into the skill). Every crawler, page signal and measurement entry has an official URL, a verbatim quote and the checked date 2026-10-21. `ai_visibility.validate_registry` enforces this, and it also keeps several facts fixed: `citation_guarantee` must be `false`; the search, training and user-fetch roles stay separate; `Google-Extended` must cite that it does not affect Google Search inclusion; user-fetch agents are never marked as obeying robots.txt; and `llms_txt` must stay `optional_unconfirmed` with `affects_ranking: false`. Bing's help pages need JavaScript and could not be read with `curl`, so for `Bingbot` the registry cites Bing's blog only and does not state the effect of a block on each Bing surface.
- **`profile-audit` gains a `google_search` entry** with two checks: "Claim your Google Search profile (only where eligible)" (`search_profile_claimed`) and "Check Search Console platform properties for your TikTok, Instagram, X or YouTube accounts" (`search_console_platform_properties`). Each check carries official sources labelled `official` (new optional `check_sources` in the registry, validated on load and shown in the checklist), and the report adds an `eligibility` alert. Google's help lists Search profiles as available in Canada, India and the United States for people aged 18 or over with 10,000+ followers on YouTube, Instagram, X or TikTok, and Search Console says platform properties are rolling out gradually. Existing registry entries are unchanged.
- `sources.RobotsCache` keeps each robots.txt it reads in `documents`, so `ai-visibility` reuses the same response instead of making a second request. Its verdicts are unchanged. Tests: `tests/test_ai_visibility.py` (32 offline tests; every online path is mocked).
- **`ai-label-check`** (offline, advisory, read-only): for a draft, variant or campaign file, or a stored post (`--post-id`, database opened read-only), tells you per target platform whether its AI-generated-content rule asks for a label (`required`, `recommended`, `not_required` or `unknown`), what to tick in the platform's own composer, the API field ReachWeaver already knows (YouTube `status.containsSyntheticMedia`, TikTok `post_info.is_aigc`), whether the platform reads C2PA Content Credentials, the stated consequence and the cited page. `--eu` adds the EU AI Act Article 50 duties for deepfakes and for AI text on matters of public interest, including the human-review exemption (wording from a secondary site, not legal advice; applies from 2 August 2026). Chinese platforms reuse the CAC labelling rule in `china.py`. X stays `unknown`: its policy page could not be read. Never blocks, approves or sends; exits 0 after a check. See [docs/AI-CONTENT-LABELS.md](docs/AI-CONTENT-LABELS.md).
- `reachweaver/ai_disclosure_registry.json`: sourced rules for YouTube, Instagram, Facebook Pages, Threads, TikTok, LinkedIn and X plus the EU AI Act Art. 50 entry, each with URL, exact quote and checked date (2026-10-21), validated by `ai_labels.validate_registry`. Shipped in the wheel and the skill bundle.
- Media manifests take an optional `realistic_synthetic: true|false` per asset. Leaving it out changes nothing; a non-boolean value is an error and `true` adds a warning pointing at `ai-label-check`.
- **`social-web-plan` (new, offline, read-only): the open social web.** Maps your accounts onto ActivityPub (Mastodon, Threads with fediverse sharing, Ghost 6, WordPress ActivityPub, Pixelfed, Lemmy, Misskey, PeerTube, Flipboard), the AT Protocol (Bluesky), Nostr, Farcaster, Matrix and diaspora*, and onto the Bridgy Fed bridge. It recommends a canonical home (owned ActivityPub site first; an editorial hypothesis), warns when a bridge or Threads sharing makes the same text reach some people twice, and lists identity steps (`fediverse:creator`, Mastodon `rel="me"` links, a domain as your Bluesky handle) and gaps. Input: `config/accounts.json` (public metadata), `--presence`, `--bridged`, `--fediverse-sharing`, `--site`/`--site-kind`, or a `--setup` file (`examples/social-web-setup.example.json`); `--json` uses schema `reachweaver.social-web-plan.v1`. It never contacts a network, reads a credential, opens the database or touches the send queue. Guide: [docs/OPEN-SOCIAL-WEB.md](docs/OPEN-SOCIAL-WEB.md).
- **`reachweaver/social_web_registry.json` (new, shipped in the wheel and the skill bundle).** 14 platforms keyed by distribution registry ids, 6 protocols, the Bridgy Fed bridge, 3 identity checks and 4 site options; every fact quotes an official page fetched 2026-10-21. Unverified points (whether a given Flipboard account is federated, Minds' default federation, the current Threads beta status) are labelled as such. Validated by `social_web.validate_registry` and `tests/test_social_web.py` (bridges and Threads federation must stay opt-in).

### Security

- **A withdrawn approval can no longer come back from a database backup (security decision item 12, owner-approved 2026-10-21).** `unapprove` and `cancel` of a post that carries an approval nonce now append one `withdrawn` line for that `(post id, nonce)` to the hash-chained approval ledger, under its lock and before the row changes. `claim_sending`, the pre-claim `check_approval_binding` gate and the ledger's own `consume` treat a withdrawn nonce like a consumed one and refuse with the fixed code `approval_withdrawn_reapproval_required` (one `approval_replay_blocked` event, `last_error` set, nothing claimed, no identity preflight, no request). Before this, a database restored from a backup taken while a post was approved would send it on the next worker run even though you had withdrawn it. `health` and the dashboard list such a row as `attention`. Normal use is unchanged: re-approving after `unapprove` draws a fresh nonce and sends; the documented recovery (`unapprove`, `show`, `approve`) works and adds no second line. Each `(post id, nonce)` holds at most one ledger line. A withdrawal is never refused because of the ledger: if the line cannot be written (missing, unreadable or broken ledger) the post is still withdrawn, the `unapprove`/`cancel` event records `ledger=unrecorded`, and the CLI prints a `WARNING` on stderr. - **`review` is owner-only.** The command catalog tags it `owner_only` and `interactive` (so `context` and `describe` list it among the owner-only commands), the plugin's agent guard refuses it in every invocation form (`review-packet`, `review-comment` and `review-status` are not affected), and the MCP server's never-exposed list includes it. - **Mastodon visibility, language and content warning are bound into the approval** (owner-approved 2026-10-21). - **Sourced UI-overlay safe zones for `media-storyboard` (issue #18 slice).** The built-in TikTok, Instagram Reels and YouTube Shorts zones were `unverified`. They are now `sourced` from first-party pages and files, accessed 2026-10-09, each with its URL, the numbers as stated, and the evidence. TikTok uses the In-Feed ads template (160/440/80 px plus a 120 px action column on 720x1280). Instagram uses Meta's Reels ad specs (14%/35%/6%). YouTube Shorts uses the Google Ads vertical-video image (288/672/48/192 px on 1080x1920). All three are **paid-ad** specs (`placement: "ads"`), and none of the sources states an organic overlay, so every check warns that organic overlays may differ. Owner zones without a source and date stay `unverified` and now add a warning to every check that uses them. The TikTok zone and the combined safe area of the default targets are stricter than before; YouTube's sourced left margin (48 px, 0.044445) is narrower than the old 0.06 convention, and its other three margins are wider.
- **`report` aggregates exact values only and no longer prints a fabricated 0 (issue #15).** A metric with no exact value on any published post is now `null` in JSON (it was 0) and `unknown` in Markdown and CSV. Each platform gains a `metrics` block with value, `exact`/`total` coverage, counts by status (a published post with no snapshot counts as `unknown`) and a separately labelled `estimated` block that is never added to the value. `import-metrics` is now all-or-nothing: a bad cell names its CSV line and nothing from that file is imported. The SYNTHETIC [weekly report example](docs/WEEKLY-REPORT-EXAMPLE.md) section A is now the `report --format markdown` output, and its fixture imports Bluesky and Mastodon views and impressions as `not_available`.


### Fixed

- **`ops-metrics --out` could overwrite the state database (issue #26, review F1).** `--out` atomically replaced any path, so `--out state/reachweaver.sqlite` replaced the database with metrics text, set it to mode 0644 and printed `database unchanged`. `ops_metrics.write_textfile` now refuses, with exit 2 and nothing written, the database itself (same path, same resolved path or a hard link, via `os.path.samefile`), any symbolic link, a directory, and an existing file whose name does not end in `.prom` or `.json`; a new file may have any name. Tests: `OutTargetTests` in `tests/test_ops_metrics.py`.
- **Read-only commands no longer create or migrate the database (issues #26, #17, review F1).** `ops-metrics` and `engagement-fetch` opened the database with `storage.connect`, which creates the file and its directory and runs `ALTER TABLE` migrations. Both now use `storage.connect_readonly` (SQLite `mode=ro`, `query_only`): a missing database is exit 2 instead of an empty one that reports zeros. On a database from an older version, `ops-metrics` names the missing columns (new `storage.schema_gaps`) and exits 2 without migrating, and `engagement-fetch` reads it unchanged (it needs only the original `posts` columns). `metrics-fetch` writes snapshots and still uses `connect`. Tests: `ReadOnlyDatabaseTests` in `tests/test_ops_metrics.py` and the read-only cases in `tests/test_engagement_fetch.py`.
- **`ops-metrics --since 999999d` crashed with an `OverflowError` traceback (issue #26, review F1).** The relative amount is now bounded by the 3650-day limit before any date arithmetic, `--now` must lie between 1970 and 9998, and `storage.parse_utc` turns an out-of-range date such as `0001-01-01T00:00:00+01:00` into a ValidationError (exit 2) for every command that parses a date.
- **`engagement-fetch` cut reply text before redacting it (issue #17, review F1).** An e-mail address, token or phone number crossing the 4000-character cap was seen only partially by the redaction patterns, so a fragment such as `john.doe@examp` or the first 4000 characters of a JWT reached the export. Redaction now runs on the first 8000 characters before the cap, a fragment split by either cut is dropped, and the result is redacted again.
- **One Bluesky reply with an empty handle made the whole `engagement-fetch` export fail (issue #17, review F1).** `write_export` rejected the document (`author_handle must be a non-empty string`). An empty or missing handle now falls back to the author's DID; a reply with neither is skipped and noted as `reply_without_author_identity_skipped`.
- **A credential with a control character could leak into `ERROR:` output (issue #5, review F1).** A `$CREDENTIALS_DIRECTORY` file ending in `\r\n` kept its `\r`, `http.client` refused the header with `ValueError("Invalid header value b'Bearer <token>\\r'")`, and the CLI printed that message, token included. `accounts.credential` now strips exactly one trailing `\n` or `\r\n` from a file and refuses any value, from a file or the environment, that still contains a C0 control character or DEL (`credential NAME contains control characters`, name only). As defence in depth, `publishers` turns a `ValueError`, `http.client.InvalidURL` or unknown-scheme error raised while building or sending a request into the fixed `PublishError("invalid_request")` (and a later `http.client.HTTPException` into `invalid_api_response_uncertain`), with the original message dropped; the CLI's top-level `ERROR:` line now passes through `privacy.redact`. Ambiguous-send classification is unchanged: a failure after `mark_write_started` is still C3 `ambiguous` and goes to `needs_review`. Tests: `ControlCharacterCredentialTests`, `ControlCharacterCliTests`, `RequestBuildErrorTests` in `tests/test_hardening.py`.

### Fixed

- `media-check` subtitle URL warnings show only scheme, host and path (`?…` marks a hidden query or fragment); a translated cue's `?token=` query string or `user:password@` no longer reaches the report.
- **Release gate: human-only rows can no longer drop their `distribution_id`.** The human-only ⇒ `blocked` rule ran only when a scorecard row had `distribution_id`, so deleting it from the `hacker_news` row let that row claim `offline_mock_tested`. Digit runs are normalised as text instead of `str(int(run))`, which raised `ValueError` past Python's 4300-digit limit; leading zeros are ignored and long runs are shortened in findings. An SRT index such as `²` or `①` (accepted by `str.isdigit()`, rejected by `int()`) crashed the check and is now a "numeric index" error, and an over-long timestamp hour field is a malformed timestamp instead of an `int()`/`float()` overflow. See [docs/CALENDAR-PLANNER.md](docs/CALENDAR-PLANNER.md).
- **Similarity tokenizer and zero-width spaces in Thai, Lao, Khmer and Myanmar.** Dropping every format character also removed U+200B where these scripts use it as the word break, so a one-word edit in ZWSP-segmented Thai scored 0.00 instead of 0.40.
