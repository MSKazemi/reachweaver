# Publishing platform matrix — assessed 2026-10-08, reconciled with the registries 2026-10-09

This page is the human-readable view of what ReachWeaver itself can deliver per platform. It is derived from two machine-readable registries and the code, and a test keeps them in step:

- [`reachweaver/platform_registry.json`](../reachweaver/platform_registry.json) (shown by `reachweaver capabilities`, validated by `reachweaver/capabilities.py`): per-format API capability, the `reachweaver_adapter` value (`live_text` or `none` in the bundled registry; `live_media` is also valid), the off-by-default `live_media_formats`, `reachweaver_reply_adapter` and video switches, auth, approval and metrics facts with sources. Details: [PLATFORMS.md](PLATFORMS.md).
- [`reachweaver/distribution_registry.json`](../reachweaver/distribution_registry.json) (validated by `reachweaver/distribution.py`): the **native** scheduling mode of each surface, with its official source. Details: [DISTRIBUTION-GOVERNANCE.md](DISTRIBUTION-GOVERNANCE.md).
- `reachweaver/postiz.py` (`PROVIDERS`/`EXCLUDED`): which platforms the optional Postiz backend accepts. Details: [POSTIZ.md](POSTIZ.md).

`tests/test_platform_matrix_docs.py` fails when the table below disagrees with those sources. If you change a registry or the Postiz mapping, update this table in the same change.

**Separate audit registry:** [`profile_audit_registry.json`](../reachweaver/profile_audit_registry.json) and [profile/post audit guide](PROFILE-AND-POST-AUDITS.md) provide offline, platform-specific owner-profile checks and content hypotheses. They do **not** grant API scopes, change adapter status, inspect accounts automatically or permit publishing. For native publishing availability use the original two registries below instead.

## Three layers that must never be merged

| Layer | What it means | Where it is recorded | Evidence that exists today |
|---|---|---|---|
| **Native platform scheduling** | The owner can schedule a post in the platform's own app or web UI. ReachWeaver plays no part. | `scheduling.mode` in the distribution registry, each with an official source | Official help pages only |
| **Mock-tested ReachWeaver adapter** | ReachWeaver code can send one approved text post through the official API. Tested with mocked HTTP only. | `reachweaver_adapter: live_text` in the platform registry; `policy.SUPPORTED_LIVE` | Offline unit tests |
| **Real owner account receipt** | A real owner account was connected and a ReachWeaver send produced a native post the owner confirmed. | Would be a dated pilot record ([FIRST-LIVE-PILOT.md](FIRST-LIVE-PILOT.md), [FIELD-PILOT-PROTOCOL.md](FIELD-PILOT-PROTOCOL.md)) | **None.** No account has been connected and no live send has been run. |

A native scheduler never implies a ReachWeaver adapter, and an adapter never implies a receipt. A suggested time from `calendar-plan` is not a provider queue receipt. A Postiz acceptance is not a platform receipt either (see the backend table).

## Adapter matrix

Column meanings:

- **ReachWeaver adapter**: the registry's `reachweaver_adapter` value. `live_text` = one approved text post via the official API, mock-tested only. `none` = no ReachWeaver send path; the manual alternative follows (the same one [TROUBLESHOOTING.md](TROUBLESHOOTING.md#blocked-platforms-and-their-alternatives) lists).
- **Via Postiz backend**: `allowed` means an owner may opt that account into the Postiz backend; it is still mock-tested only and still behind every ReachWeaver approval gate. `refused` means `postiz.py` rejects the account configuration.
- **Native scheduling**: the distribution registry's `scheduling.mode` for the same surface (`dev` and `facebook_pages` there are `devto` and `facebook` here).
- **Owner live receipt**: `none` for every row. It may change only with a dated, owner-confirmed native post URL from a real pilot.
- **Media**: ReachWeaver uploads no media on any platform. Mock-tested media adapters exist for Mastodon images (#13, proposal), Instagram single images (#20), YouTube video (#22) and TikTok creator-inbox video (#23), all owner-approved 2026-10-09 and disabled until a live receipt: the capability registry lists no `live_media_formats`, every video switch is `off` and `policy.SUPPORTED_LIVE_VIDEO` is empty, so no upload path is reachable. The column lists the offline tools that cover the platform: `media-check` (sourced per-platform limits in `media.CONSTRAINTS`), `media-storyboard` (video targets and image specs in `storyboard.py`) and `manual-export` (creator packages in `manual_export.py`).
- **Analytics**: `metrics` and `import-metrics` record owner-exported native snapshots for every platform. Only Bluesky and Mastodon also have `metrics-fetch --online`.

## Notes

`draft` and `export` mean that a text draft or package can be prepared locally; neither implies an integrated platform API. Neither skills nor provider marketing pages authorize bypassing platform app review. Recheck official documentation before adding any API integration.

The distribution registry tracks 56 planning surfaces, including country and community channels that have no row here. None has a connected owner account in ReachWeaver. Only the four `live_text` adapters above (Bluesky, Mastodon, Telegram, LinkedIn member) are enabled, and they are mock-tested only. The Threads, Instagram, Facebook Page, YouTube and TikTok adapters, Mastodon images and Bluesky/Mastodon replies are mock-tested too but disabled until a live receipt, so those surfaces stay manual; every other surface is manual, draft or not applicable.

Official references: [Bluesky](https://docs.bsky.app/docs/tutorials/creating-a-post), [Mastodon](https://docs.joinmastodon.org/methods/statuses/), [Telegram](https://core.telegram.org/bots/api#sendmessage), [LinkedIn](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api), [TikTok](https://developers.tiktok.com/docs/en/content-posting-api-get-started), [YouTube](https://developers.google.com/youtube/v3/docs/videos/insert), [Postiz public API](https://docs.postiz.com/public-api/introduction). Public-counter sources for `metrics-fetch` are cited in `reachweaver/metrics_fetch.py` (Bluesky `app.bsky.feed.getPosts` lexicon; Mastodon `GET /api/v1/statuses/:id` and the Status entity, fetched 2026-10-08).

**Operational truth:** nobody's account has been authorized or tested here. The `live_text` adapters and the Postiz backend are API-shaped implementations with mocked unit tests, not verified integrations or guarantees of delivery. Accounts must be linked and tested with explicit owner involvement.

**Online connection check (2026-10-08):** `connect-check --account ID --online` performs authenticated identity probes without posting, for Bluesky, Mastodon, Telegram and LinkedIn. The Instagram, TikTok, YouTube, Threads and Facebook probes exist but are refused before any credential read while those adapters are disabled. `postiz-check --account ID --online` is the read-only equivalent for a Postiz-backed account. Both were verified only by offline mocked tests. Review provider scopes and permissions on the day of the pilot.

**Planning versus posting:** `calendar-plan` proposes audience-local timing for configured accounts, but cannot send or remotely queue posts on platforms whose adapter is `none`. The optional `--apply` records **local due times only** for already-approved Bluesky, Mastodon, Telegram and LinkedIn member text posts. Other platforms need native scheduling by the owner, official app permissions or a future consented adapter. Full instructions: [calendar planner](CALENDAR-PLANNER.md).
